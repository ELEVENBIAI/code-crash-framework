## Summary

Die Integrations-/Kohärenz-Story: bringt die 13 Infra-Layer aus dem Katalog (BOO-220) als **Projekt-Artefakt** ins
ARCHITECTURE_DESIGN-Template und verdrahtet sie **weich** in den Lebenszyklus. Neuer Abschnitt **„Infra-Layer"** =
**13-Zeilen-Tabelle** (`Layer | Entscheidung (1 Satz) | Status: ok / n.ok / n/a (bewusst) | Verweis`) als **Single Entry
Point** pro Projekt — eine Zeile je Layer, jede verweist auf den Katalog. §5 (Qualitäts-Dimensionen) bleibt **unverändert**;
Security/Monitoring/Performance verweisen per Querverweis auf §5 (keine Dopplung). Dazu: **weiche** Gate-Verdrahtung
(`/ideation`, `/architecture-review`, `/implement` — Prompt/Gegencheck, Hard-Gate nur im Compliance-Modus) und
**Framework-Kohärenz** (knowledge-onboarding-Mapping, Bootstrap-Post-Install-Hinweis, HANDBUCH-Onboarding-Sektion,
Artefakt-Landkarte). DE+EN, betroffene Skills Version-Bump, `docs-drift` rc=0.

## Why

Der Katalog (BOO-220) ist die „Lehrbuch"-Ebene — stack-neutral, framework-weit. Ohne ein **Projekt-Artefakt** bleibt die
Lücke zwischen Prototyp und Produkt unsichtbar: Niemand sieht, welche Layer für *dieses* Projekt entschieden, offen oder
bewusst irrelevant sind. Die 13-Zeilen-Tabelle macht den Stand pro Projekt **auf einen Blick** sichtbar (Single Entry
Point), die weiche Verdrahtung sorgt dafür, dass die Frage zum richtigen Zeitpunkt (Feature mit Infra-Bezug, Architecture-
Review) **gestellt** wird — ohne den „später füllen"-Pfad zu blockieren (Leichtgewicht-Designprinzip). Erst mit diesem
Artefakt kann BOO-223 den geführten Layer-Abgleich operationalisieren.

## What

1. **ARCHITECTURE_DESIGN-Template: neuer Abschnitt „Infra-Layer"** (`bootstrap/references/architecture-design-template.md`
   + `.en`). Platzierung **nach §5 (Qualitäts-Dimensionen), vor §6 (Referenzen)** — die Infra-Achse direkt nach der
   Qualitäts-Achse. 13-Zeilen-Tabelle:
   `| Layer | Entscheidung (1 Satz) | Status: ok / n.ok / n/a (bewusst) | Verweis |`. Eine Zeile je Layer (1–13 in der
   Katalog-Reihenfolge), **lean**. Spalte „Verweis" zeigt auf den Katalog
   (`cloud-system-engineer/references/infrastructure-dimensions.md` §Layer). Kurz-Intro: zwei Achsen, §5 bleibt SSoT der
   Qualitäts-Achse; für Security/Monitoring/Performance verweist die Infra-Zeile per Querverweis auf §5 statt zu doppeln.
2. **Tiefe on-demand:** eine Zeile *darf* in „Verweis" auf ein Projekt-Sub-MD zeigen (z.B. `DB_SCHEMA.md`, `IAM_POLICY.md`,
   `RECOVERY_PLAN.md`) — **nur wenn nötig**, kein Vorbau. Im Template als Hinweis dokumentiert, keine Skelett-Dateien.
3. **Gate-Verdrahtung (weicher Prompt; Hard-Gate nur im Compliance-Modus):**
   - **`/ideation`** — bei Feature mit Infra-Bezug (`change_type: infrastructure` bzw. infra-berührende Stories) auf
     **leere/`n.ok` Layer-Zeilen** hinweisen. Weicher Prompt, kein Block.
   - **`/architecture-review`** — unausgefüllte/abweichende Layer **finden** + zur Nacharbeit anstoßen (ermöglicht den
     „später füllen"-Pfad). Drift-Erkennung gegen die Tabelle.
   - **`/implement`** — Gegencheck Spec ↔ Infra-Layer (berührt die Story einen Layer, dessen Tabellenzeile leer/`n.ok` ist?
     → Hinweis).
4. **Framework-Kohärenz (PFLICHT — Whole-Framework-View):**
   - **knowledge-onboarding**: Mapping-/Routing-Tabelle um das Infra-Layer-Artefakt erweitern (infra-bezogene Bestands-Doku
     wie DB-Schema/IAM-Policy → Infra-Layer-Sektion bzw. Sub-MD). ARCHITECTURE_DESIGN.md ist bereits Tier-0 — die Routing-
     Rubric (`knowledge-onboarding/references/routing-rubric.md`) bekommt die Infra-Sub-MD-Kategorie.
   - **Bootstrap-Post-Install-Checkliste**: Hinweis (kein Zwang) — „13 Layer + Fragen sind im ARCHITECTURE_DESIGN drin;
     Default-Standards ok → loscoden; eigene Vorgaben → später `/infrastructure-onboarding` (BOO-223)".
   - **HANDBUCH**: neue Onboarding-Prozess-Sektion (DE+EN) — wann Katalog-Abgleich, wann lazy-fill, wie die zwei Achsen
     zusammenspielen.
   - **Artefakt-Landkarte** (`docs/onboarding/artefakt-landkarte.md` + `.en`): die Infra-Layer-Tabelle einordnen (wo sie
     sitzt, was sie referenziert).
5. **Version-Bump betroffener Skills** (SKILL+README DE+EN, version: == **Version:**): bootstrap (Template), ideation,
   architecture-review, implement, knowledge-onboarding. `docs-drift` rc=0, DE+EN-Parität.

## Constraints

- **Weich, nicht hart:** Die Gate-Verdrahtung ist ein **Prompt/Hinweis**, kein blockierendes Gate — Ausnahme: expliziter
  Compliance-Modus. Der „später füllen"-Pfad muss offen bleiben (Leichtgewicht-Designprinzip: kein >30-Min-Operator-Overhead
  ohne Compliance-Argument).
- **§5 unberührt:** Die Qualitäts-Dimensionen (§5) bleiben wortgleich; keine Migration, keine Umnummerierung. Die Infra-
  Tabelle **verweist** auf §5, dupliziert nicht.
- **Single Entry Point, lean:** eine Zeile je Layer. Tiefe nur on-demand via „Verweis" auf Sub-MD — kein Skelett-Vorbau.
- **Anti-Fabrikation kritisch:** Diese Story fasst **fünf Skills + HANDBUCH + Landkarte** an. Sub-Agents fabrizieren
  Schritt-/Versions-Details → jede Skill-Änderung gegen die **reale** SKILL-Struktur grounden (wo genau hookt der weiche
  Prompt?), Lead-Cross-Check vor Commit. `change_type: infrastructure`-Verdrahtung gegen die echte Stelle in `/ideation` +
  `non-code-flow`/CONVENTIONS-Change-Type-Matrix verifizieren, nicht erfinden.
- **Katalog-Verweis stabil:** Zeilen-Verweise zeigen auf `infrastructure-dimensions.md` (BOO-220, auf main) — Pfad/Anker
  gegen die reale Datei prüfen.
