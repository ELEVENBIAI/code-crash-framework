## Summary

Bootstrap erzeugt ein natives **Status-Line-Custom-Script** `bootstrap/templates/statusline.sh`, das
in `runtime_target: claude-code` (Schalter A) live im Claude-Code-Prompt anzeigt:

```
Sonnet 4.7 | 142k/200k ctx | Worker-Equiv: 4.2h / 16h | Story BOO-87 | $4.20
```

Das Skript liest aus den bereits existierenden Datenquellen — ccusage-Snapshot
(`docs/financials/sprint-costs.md`, BOO-189), Worker-Equivalent-Verrechnungssatz
(`docs/financials/worker-equivalent-baseline.md`, BOO-190) und der laufenden Story (Linear/`meta.json`).
Es wird über `.claude/environment.json` (bzw. `.claude/settings.json` `statusLine`) referenziert.
Als setup-integriertes Feature folgt es dem **Pflicht-Quartett**: Bootstrap-Hinweis + HANDBUCH-Sektion
(Anhang AQ) + `migrate_boo_205()` + `verify-setup.sh`-Check. Native Status-Line statt Eigenbau-UI ist
der Build-vs-Buy-Befund (ADR-1): gleiche Sichtbarkeit, schlanker.

## Why

ADR-1 (Build-vs-Buy) ordnet das Worker-Equivalent-Live-Display der Kategorie „Substituierbar" zu: die
native Status-Line liefert das gleiche Ergebnis ohne Eigenbau-UI. Ohne diese Story bleibt das
Worker-Equivalent (zweite Steuerungs-Dimension, ADR-D) nur im Sprint-Report sichtbar — nicht **während**
der Arbeit. Der Operator soll Modell, Token-Budget, Story-Budget (Worker-Equiv) und KI-Kosten live im
Prompt sehen, ohne ein Tool zu wechseln. Das macht die Steuerungs-Dimension im Moment der Entscheidung
nutzbar, nicht erst in der Retrospektive.

## What

1. **Status-Line-Script** — `bootstrap/templates/statusline.sh` (neu). Bash-only, liest stdin-JSON von
   Claude Code (Modell, `context_used`/`context_window`, `cwd`) und reichert an aus:
   - **Modell + Token-Budget:** aus dem von Claude Code an die Status-Line übergebenen JSON.
   - **KI-Kosten ($):** letzter ccusage-Snapshot in `docs/financials/sprint-costs.md` (BOO-189; Text-Format,
     defensiv geparst — fehlt die Datei oder ein Wert, wird das Feld weggelassen, kein Fehler).
   - **Worker-Equiv (h/h):** aktueller Sprint-Report `docs/financials/sprint-*-worker-equivalent.md`
     bzw. Verrechnungssatz aus `docs/financials/worker-equivalent-baseline.md` (BOO-190/191/193).
   - **Story-ID:** aus dem aktiven Branch-Namen (`tobiaschschmidt/boo-XXX-…`) oder dem jüngsten
     `journal/reports/local/*/meta.json` (`story_id`).
   - **Defensiv:** jedes Feld optional; fehlende Quelle ⇒ Feld entfällt, Skript endet immer mit rc=0.
2. **`.claude/environment.json`-Referenz** — Bootstrap trägt die Status-Line-Referenz im
   generierten Projekt ein (`statusLine`-Verweis auf `statusline.sh`). Triplikat-Konvention: Heredoc in
   `bootstrap/references/file-templates.md` (DE) **+** `file-templates.en.md` (EN) **+** `migrate_boo_205()`
   in `bootstrap/scripts/migrate-to-v2.sh` — byte-identisch (Lead schreibt alle drei).
3. **Schalter-A-Kopplung** — Status-Line wird nur ausgerollt/aktiviert, wenn `runtime_target: claude-code`.
   Bei `codex`/`cross-tool`/`unknown` kein Status-Line-Setup (analog `native_paths`-Inaktivität). Lese-Muster
   wie `/implement` Schritt 0d (CLAUDE.md `native_paths`).
4. **Bootstrap-Hinweis** — `bootstrap/SKILL.md` (+ `.en.md`): bei `runtime_target: claude-code` Hinweis,
   dass die Status-Line ausgerollt wird, mit einem Satz was sie zeigt (kein eigener Frage-Schritt nötig —
   die Aktivierung folgt aus Schalter A; reiner Hinweis + Verweis auf Anhang AQ).
5. **HANDBUCH-Sektion „Status Line"** — neuer **Anhang AQ** (`HANDBUCH.md` + `.en.md`): erklärt die
   Custom-Variablen (Modell, ctx, Worker-Equiv, Story, $), die Datenquellen, die Schalter-A-Kopplung und
   wie der Operator das Skript anpasst. TOC + Kapitel-13-Signpost-Tabelle (Anhang-Zähler) mitziehen.
6. **`verify-setup.sh`-Check** — neue Sektion (z.B. §5c): bei `runtime_target: claude-code` prüfen, dass
   `statusline.sh` vorhanden + ausführbar ist und in `.claude/environment.json`/`settings.json` referenziert
   wird. Bei anderem `runtime_target` Check überspringen (kein Fehler).
7. **Version-Bumps:** `bootstrap` 3.43.0 → **3.44.0** (SKILL + README, DE+EN, docs-drift-Parität).
8. `docs-drift` rc=0; diese Spec → Result; Vault-Skill-Doku `bootstrap.md` (+ `.en`) nachziehen; Release
   im Sammel-Cut v0.13.0.

## Constraints

- **Native Status-Line, kein Eigenbau-UI** (Build-vs-Buy/ADR-1): das Skript reichert nur an, was Claude
  Code bereitstellt + persistierte Datenquellen — keine eigene Render-/UI-Schicht.
- **Schalter-A-Kopplung** wie bei allen Native-Pfaden: inaktiv bei `runtime_target ≠ claude-code`.
- **Defensiv & idempotent:** jedes Feld optional, Skript endet immer mit rc=0; `migrate_boo_205()`
  idempotent (`ensure_file`/`append_if_missing`).
- **Keine Secrets** in die Status-Line oder ins Skript schreiben; ccusage-$-Wert ist ein Schattenpreis
  (Max-Pro) bzw. Echtkosten (API) — kein Key-Material.
- **AC-Pfad-Treue:** Das Quell-Template liegt — abweichend von der bisherigen `bootstrap/references/hooks/`-
  Konvention — unter `bootstrap/templates/statusline.sh`, weil das AC diesen Pfad wörtlich nennt
  (neues Verzeichnis, bewusst). Siehe Umsetzungs-Hinweise.
- **Anhang-Buchstabe** AQ (gegen frisches `HANDBUCH.md` final vergeben — höchster aktuell = AP).
- **Skill = Instruktionen + ein Bash-Skript.** Die Trigger-/Ausroll-Logik = präzise SKILL.md-Anweisungen;
  das Skript selbst ist das einzige Code-Artefakt.
